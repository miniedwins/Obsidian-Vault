## Q1：傳遞大量資料時，需要自己拆封包嗎？需要自己計算 MIC 嗎？

### 答：**完全不需要，`mi` 工具負責所有拆包與 MIC 計算**

這是整個架構中最關鍵的設計：`mi` 是一個 **NVMe-MI 完整 stack**，你只需要指定「要傳什麼資料」，底層全部自動處理。

```
你下的命令（只需指定資料內容）
              ↓
┌─────────────────────────────────────────────────────────────┐
│           mi 工具（自動做以下所有事）                         │
│  1. 根據 TUS（Transmission Unit Size）計算需要幾個封包       │
│  2. 自動將資料分割成多個 MCTP packet                          │
│  3. 每個封包自動設定 SOM / EOM / PktSeq bits                  │
│  4. 計算並附加整個 Message 的 MIC（CRC-32C，最後 4 bytes）   │
│  5. 計算每個 SMBus frame 的 PEC（CRC-8，硬體層）             │
└─────────────────────────────────────────────────────────────┘
              ↓
   設備收到多個 MCTP 封包（smbus_rsp[0]...smbus_rsp[N]）
```

### 具體例子：VPD Write 256 bytes（跨多個封包）

從 [08.13_VPDWrite.sh L206](file:///C:/Users/edwin/Desktop/SANBlaze/scripts/sanblaze_py_api/scripts/V22_IOL_NVMe_MI/SMBus/V22_IOL_NVMe_MI_SMBus_08.13_VPDWrite.sh#L206) 和 [04.08_InvalidVPDWriteSize.sh L68-69](file:///C:/Users/edwin/Desktop/SANBlaze/scripts/sanblaze_py_api/scripts/V22_IOL_NVMe_MI/SMBus/V22_IOL_NVMe_MI_SMBus_04.08_InvalidVPDWriteSize.sh#L68-L69) 可以看到：

```bash
# 你只寫這一行，就算資料跨越 5 個 MCTP 封包也好
# mi 工具自動拆包、自動加 MIC、自動設 SOM/EOM
mi -t 0x1 -T smbus -s $sanblaze -d $slot 0x6 \
   -o 254 -l 2 -w cccc -v > $file1
#               ↑ offset   ↑ length  ↑ write data（自動分包）

# 更大的 write（mi 自動處理多個 MCTP 封包）
mi -t 0x1 -T smbus -s $sanblaze -d $slot 0x6 \
   -o 0 -l 256 -w <256-bytes-hex> -v
```

### 封包分割的依據：TUS（Transmission Unit Size）

```
NVMe-MI Message 大小          MCTP 封包數量
─────────────────────────────────────────────
TUS = 64 bytes，Message = 256 bytes
→ (256 + MIC 4bytes) / (64 - MCTP Header) ≈ 5 個封包

mi 工具內部會先查詢 TUS，再自動計算分割數量
你完全不需要手動計算
```

### MIC 計算責任

| 責任 | 誰負責 |
|---|---|
| MIC 位置（Message 最後 4 bytes）| mi 工具計算並自動附加 |
| MIC 演算法（CRC-32C） | mi 工具內建 |
| 多封包情況下 MIC 只計算一次 | 正確，MIC 是 **Message 層**保護，不是封包層 |
| 你需要手動計算 MIC | ❌ **不需要** |

## Q2：可以在多封包中的**某一個特定封包**加上錯誤的 MIC 嗎？

### 答：**這裡需要嚴格區分兩個概念，且有重要限制**

### 首先：MIC 在封包中的位置

```
多封包情況（5 個 MCTP 封包）：

封包 1 [SOM=1]:  MCTP Header | NVMe-MI Header | Data Part 1
封包 2         :  MCTP Header | Data Part 2
封包 3         :  MCTP Header | Data Part 3
封包 4         :  MCTP Header | Data Part 4
封包 5 [EOM=1]:  MCTP Header | Data Part 5 | MIC[3] MIC[2] MIC[1] MIC[0]
                                               ↑ MIC 只在最後一個封包的尾端
```

> [!IMPORTANT]
> **MIC 只存在於最後一個封包（EOM=1 的那個）的末尾 4 bytes。**  
> 它不存在於中間封包。所以「在某個中間封包注入錯誤 MIC」這個需求，技術上沒有對應的欄位。

### 可以做到的事：用 `-M 1` 讓最後一包的 MIC 值錯誤

```bash
# -M 1 讓 mi 故意送出錯誤的 MIC（影響的是 EOM 封包末尾的 4 bytes）
mi -t 0x1 -T smbus -s $sanblaze -d $slot 0x4 0x3 -p 0 -M 1 -v

# 設備收到完整的 5 個封包後，在最後一包驗證 MIC
# 發現 MIC 錯誤 → 整個 Message 被 silent drop
```

這在 [05.06_MessageIntegCheck.sh L91-92](file:///C:/Users/edwin/Desktop/SANBlaze/scripts/sanblaze_py_api/scripts/V22_IOL_NVMe_MI/SMBus/V22_IOL_NVMe_MI_SMBus_05.06_MessageIntegCheck.sh#L91-L92) 中可以看到。

### 進階：用 `-m` 直接控制 raw bytes 做封包級別注入

若你的目標是在某個**特定封包**注入特定的 bad bytes（例如破壞封包 3 的資料），需要用 `-m` 搭配 `-H` 手動組裝每一個封包：

```bash
# 這種方式需要你自己拆包 + 手動控制每個封包的 raw bytes
# 但此方式目前腳本中沒有現成的 "分封包注入" 功能

# 現有腳本能做到的：
# ① 整個 message 送壞 MIC（-M 1）→ 05.06
# ② 注入壞 MCTP Header（-H 參數）→ 01.04.x，但這是針對單一小命令

# 目前現有腳本 "沒有" 以下功能：
# × 對多封包 write 命令的「第 N 個封包」單獨注入壞資料
```

### 完整對照表

| 目標 | 是否可行 | 方式 | 限制 |
|---|---|---|---|
| 送出大量資料，不管分包 | ✅ 完全可行 | `-l length -w data`，mi 自動分包 | 無 |
| 讓整個 Message 的 MIC 錯誤 | ✅ 可行 | `-M 1` | 影響整個 Message，不是單一封包 |
| 讓某個中間封包帶有壞 MIC | ❌ **不存在** | N/A | MIC 只在最後一個封包的尾端，中間封包沒有 MIC 欄位 |
| 破壞某個中間封包的資料 bytes | ⚠️ 理論可行 | 手動用 `-m` 組裝 raw bytes 逐封包送 | **需要自行實作整個多封包傳送邏輯**，超出現有 `mi` 命令的高層封裝 |
| 注入壞 MCTP Header（SOM/EOM）| ✅ 可行 | `-H` 覆蓋 MCTP Header | 一次只能針對單一命令（小型封包），大型多封包暫無 |

### 小結圖

```
正常多封包請求：
Pkt1[SOM] → Pkt2 → Pkt3 → Pkt4 → Pkt5[EOM, MIC=OK] → 設備接受

-M 1 的效果：
Pkt1[SOM] → Pkt2 → Pkt3 → Pkt4 → Pkt5[EOM, MIC=BAD] → 設備 silent drop

你想要的「中間封包注入壞 bytes」：
Pkt1[SOM] → Pkt2 → Pkt3[BAD_DATA] → Pkt4 → Pkt5[EOM]
→ 需要完全繞過 mi 高層封裝，手動以 raw bytes 逐包發送
→ 現有 mi 命令 -m / -H 只能對「整個命令」操作，無法指定「第 N 包」
```

如果你有這種「對某一個中間封包單獨注入錯誤」的需求，這會是 Python Module 的重要開發目標之一——實作一個**可以逐封包手動組裝並發送**的低層介面。需要的話我可以幫你設計這個架構。
