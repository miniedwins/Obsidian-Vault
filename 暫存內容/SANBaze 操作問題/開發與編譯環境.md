
## C/C++ 開發與編譯環境

- **函式庫整合與編譯路徑**：
    
    - 系統預設的編譯工具鏈（Toolchain）為何？若要連結自定義的 `.so` 或 `.a` 檔，是否有建議的目錄規範（如 `/usr/local/lib` 或專屬目錄）？
        
    - 編譯時是否需要特定的編譯旗標（Compiler Flags）以與 SANBlaze 的系統環境（如 LTO 或特定架構優化）保持一致？
        
- **硬體控制深度 (Low-level vs. API)**：
    
    - 系統提供的是**底層暫存器映射（Memory Mapped I/O, MMIO）**的直接存取權限，還是必須透過封裝好的 **User-space 驅動 API**？
        
    - 是否支援開發自定義的核心模組（Kernel Module），還是所有測試邏輯都限制在 User-space 執行？
        
- **版本相容性與 ABI (Application Binary Interface)**：
    
    - 當機器韌體或作業系統核心（Kernel）更新時，User-space 的 API 是否保證**向下相容（Backward Compatibility）**？
        
    - 如果更新涉及核心驅動變動，自編譯程式是否會因為 ABI 改變而必須重新編譯（Recompile）或重新連結（Relink）？

- **開發流程：在地編譯 vs. 交叉編譯 (Native vs. Cross-compile)**：

	- 系統是否支援在外部環境（如我的 Ubuntu 22.04 開發機）進行**交叉編譯**後再部署到 SANBlaze？還是必須在 SANBlaze 機器內部直接編譯？
	    
	- 是否有提供對應的 **SDK 或 Sysroot** 供離線開發使用？


由於您對嵌入式與低階協議（如 NVMe-MI）有經驗，建議您可以特別詢問：「**如果我需要針對非標準（Vendor Specific）的 NVMe 指令進行精準的 Timing 測試，C 語言 API 的延遲（Latency）表現如何？**」
